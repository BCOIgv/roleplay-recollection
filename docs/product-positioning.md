# 朝花夕拾：产品方向、生态位与命名诊断

2026-11-07 后续落实：[命名与展示规范](naming.md)已统一；[漫游边界研究](wandering-boundaries.md)和[独立价值测试计划](evaluation-plan.md)提供候选方案与后续执行协议。下文保留 11 月 6 日诊断日期与证据范围，不将新提案记作已实现效果。

评估日期：2026-11-06（Asia/Shanghai）。依据当前工作区代码与公开一手资料；代码基线为 `65ef240`。本次评估没有启动真实模型实验、查看生产运行状态或发送消息。

## 判断

**作为 AI 伴侣与角色扮演的可选行为层，这个切入点成立；强需求和独立安装价值尚未得到证明。** 当前实现有清晰的行为契约，也有比概念演示更完整的状态管理；自然度、用户愿意持续开启的比例，以及相对简单定时提示的收益仍缺证据。

文档确实有定位问题：上一轮把“长期记忆”放到标题和首句，读者自然会把项目归入记忆存储与召回工具。但文案无法替代产品验证。“独特的设计取向”不能直接写成“不可替代”。

## 第一步：方向诊断

### 1. 可以从记忆系统中剥离，但不能将长期记忆等同于静态存储

长期记忆描述信息跨时间保留与使用的能力；回忆、内省、巩固和触发策略描述如何处理与使用记忆。两者属于可以组合的维度。

独立模块的接口可以是：读取已有材料和当前可见边界，接收宿主提供的空闲状态与模型服务，维护回忆机会，运行有界漫游，再返回暂定想法或表达意愿。这个边界有工程意义，尤其适合已经拥有角色、记忆与消息通道的开发者。

但生态并非只提供被动记忆：

| 一手资料 | 已存在的能力 | 对本项目的约束 |
| --- | --- | --- |
| [Mem0 工作原理](https://docs.mem0.ai/core-concepts/how-it-works) | 从对话抽取可复用事实并按查询检索 | Mem0 已有模型参与的记忆处理，不能简化为向量数据库 |
| [Mem0 Platform Dream](https://docs.mem0.ai/platform/features/dream) | 后台归纳模式、处理过时事实和合并重复；后台归纳的可用性与套餐、配置有关 | 后台处理与“做梦”都不能作为本项目独有声明；也不能把 Platform 功能无条件归到 OSS 包 |
| [Letta Memory & dreaming](https://docs.letta.com/configuration/memory) | 后台回顾对话、提炼经验并更新记忆 | 无用户即时提问也进行记忆工作已有实现；其文档强调的目标是经验与记忆改进 |
| [SillyTavern Extension-Idle](https://github.com/SillyTavern/Extension-Idle) | 用户空闲一段时间后触发提示继续对话 | “空闲时能说话”本身不构成有力区分 |
| [EchoText](https://github.com/mattjaybe/SillyTavern-EchoText) | 主动消息与多种触发，其中包含 shared-memory / Memory Nudge | 连“主动提起共同旧事”也已有相邻实现；此处按其公开说明评估，未做运行质量比较 |
| [Generative Agents，UIST 2023](https://research.google/pubs/generative-agents-interactive-simulacra-of-human-behavior/) | 记忆、反思与行为规划的组合 | 记忆转化为角色行为的思路并非本项目首创；论文结果不能直接替本插件背书 |

当前合理的区分是**优化目标与模块组织**：以没有指定产出任务的角色回忆为中心，允许停留、转念、沉默，区分暂定想法与表达意愿，并提供宿主可以控制的投递生命周期。这是差异化组合，不是排他的技术能力。

### 2. 痛点是否足够痛

对普通问答、企业知识库或任务助手，这通常是低优先级能力。用户先要的是事实正确、上下文完整与任务完成；无请求的表达还可能增加打扰。

对持续使用同一角色的 AI 伴侣和 RP 用户，存在一个合理假设：他们希望角色偶尔自行提起共同经历，体现相处的延续，而不总靠用户主动点题。目标用户可感知的是“这句话与过去相处有关、出现得合适、值得听”，而不是后台有多少 thought 对象。

这个假设尚不能判定为伪需求，也不能直接当成强需求。尤其需要区分：用户想要更好的回复、偶尔的旧事分享、还是一个持续进行的后台漫游过程。前两者有价值，不自动证明第三者必须单独存在。

如果私人想法既不影响后续回复，也不产生用户愿意收到的表达，单纯多跑后台模型不会形成可感知价值。允许沉默仍然合理，但它需要置于整体体验中验证，不能用“没有输出所以不可评价”回避评估。

### 3. 当前实现的真实长处

当前[独处实现](../src/solitude.mjs)已包含持久化机会、进入条件、预算、动作协议、暂定想法、表达候选及投递结算；[全局运行](../src/global-core.mjs)还处理来源重验与受众权限。模块化价值主要在这些可组合约定与状态生命周期。

具体值得保留的设计有：

- 没有当前问题、工作汇报或消息配额要求；普通小事也可以成为材料。
- `leave` 和无内容产出是有效路径，回想不需要用发消息来证明发生过。
- 想法不自动成为事件或事实，表达也不自动等于投递。
- 对话、预算、来源可见性与投递回执具有明确约束。

这些约束构成可复用实现的价值。单独的“定时器 + 回忆提示词”很容易做出概念演示；把状态与真实宿主协调完整，才是更有分量的工作。

### 4. 尖锐的问题

**“无目的”仍是受约束的策略。** 当前局部关联使用词面、标签和加权选择；默认最多 2 步，配置上限 3 步，单日预算默认 2 次调用。独处时限是上限，不代表持续思考那么久。可以称为无指定产出任务的有界漫游，不能仅凭这些规则声称已经模拟出人类意识流。

**最直接的替代方案比 RAG 更简单。** 真正需要比较的是：同样的角色、记忆、模型、时间窗口与成本下，用一次定时提示生成旧事分享，是否已经足够好。只证明能生成话语无法证明需要单独安装本模块。

**承诺的体验与交付边界之间仍有距离。** 核心不观察平台消息、不驻留调度，也不内置真实模型执行器或发送通道。宿主需要提供身份、空闲状态、模型、打断和投递。这个边界在架构上合理，但集成成本越高，插件越需要证明收益。

**独立于存储是方向，现成互通仍不足。** 当前只读 JSON/JSONL/SQLite 来源可以复用资料，但不等于有经过验证的 Mem0、任意 RAG 或各聊天平台原生连接器。“无需迁移所有记忆”可以作为方向和已有只读能力说明，“直接接上任何记忆系统”还不能承诺。

**引用校验不等于语义真实性。** 当前锚点约束确认引用出现在可见材料中，并不能证明生成整句话没有过度解释。真实模型是否反复使用套话、牵强联想或重复开场，仍需要专门评估。

仓库[验证说明](verification.md)主要提供合成测试、脚本化模型和安装检查。它们支持工程行为的判断，不能替代真实自然度或用户需求的对照证据；这不意味着项目其他环境从未进行过真实模型调用。

### 5. 建议定位与功能边界

推荐定义：

> 朝花夕拾是已有记忆之上的 AI 角色回忆行为层：在宿主提供的空闲机会中运行有界漫游，允许安静结束，保留暂定想法，并将可选表达交给宿主择机取用与投递。

与存储、检索、巩固组件总体互补，具体能力会重叠；与角色运行框架、主动聊天策略之间则既可组合，也存在替代关系。无需把所有相关项目都归成“下层存储”。

| 层次 | 建议责任 |
| --- | --- |
| 已有记忆系统或本地轻量经历库 | 材料保存、来源维护、检索与可见投影 |
| 朝花夕拾 | 回忆机会、有界漫游、暂定想法、表达候选及其状态约定 |
| 角色宿主 | 可信身份、空闲信号、模型调用、打断、回复整合与平台投递 |

下一步优先完成一个真实宿主的参考接入和一种外部记忆来源的完整适配。把局部记录作为轻量起步方案，避免为竞争“大而全记忆平台”继续扩展向量库、知识图谱或人格数值系统。

“主动表达”比“主动倾诉”更适合作为公开功能名：当前产物是短表达候选，覆盖分享旧事、轻微联想或一句想说的话，不承诺长篇情感倾诉。“灵魂”可作为体验比喻，工程文档应写可观察的行为。

### 6. 如何判断是否值得继续做

建议先比较三种方案，保持记忆、模型、角色设定、候选长度、投递窗口和成本预算尽量一致：

| 方案 | 要回答的问题 |
| --- | --- |
| 只有被动记忆 | 增加任何回忆表达是否有实际收益 |
| 简单定时提示 + 旧事材料 | 是否需要多步漫游、私人想法和独立状态协议 |
| 朝花夕拾 | 完整行为链是否稳定改善体验，且值得集成与维护 |

先用盲评比较候选的贴合、自然、重复、牵强联想和事实边界，再在愿意接收此类表达的少量真实用户中观察保留意愿、打扰反馈和成本。回复率只是信号之一，不能替代用户是否想继续开启。

默认机会间隔为 72–120 小时，一段短试运行可能只有少数机会。应记录实际机会与有效样本，不能把运行天数等同于需求验证。也不要为了快速积累样本而将高频打扰当成正常产品行为。

如果完整方案与简单定时提示相比没有稳定优势，合理调整是收缩为宿主内的一种可选回忆策略，保留有用的状态组件。若用户只接受融入正常回复的旧事，可以优先这种表达方式。若两类表达都缺乏保留意愿，就应降低项目投入，而非继续增加“更像人”的措辞。

这些是建议的验证方法，本次没有执行真实用户实验。

## 命名评估

“朝花夕拾”与重拾往事很贴合，也为项目提供了比通用技术名更清楚的文学品牌。但名字本身不说明空闲触发、角色漫游或主动表达，单独使用容易被理解为回忆录、摘录或归档工具。与鲁迅散文集同名，也容易混入文学搜索意图；这里没有据此推算搜索量或排名。

建议保留文学名，用功能副标题补齐信息：

- 中文标题：**朝花夕拾 · Roleplay Recollection**。
- 中文副标题：**AI 角色的独处回忆与主动表达**。
- 英文标题：**Roleplay Recollection**。
- 英文副标题：**Idle recollection, mind-wandering, and optional outreach for AI characters**。
- 仓库与包名：继续使用 `roleplay-recollection`。

“Dawn Blossoms Plucked at Dusk”可在英文入口解释意境，但不必作为新的包名或主要搜索入口。About 中加入 roleplay、companion、memories 和 Node.js 等类别词；将长期记忆放在关系说明中，避免再次抢占产品主定位。具体推荐元数据见[文档诊断](documentation-review.md)。
